Nothing here is required reading to use the site; it's for whoever's curious, or wants to build something like it themselves.

1. The one-paragraph version

There is no server, no database, and no backend process that answers requests. Every page is a static HTML file with vanilla JavaScript, hosted for free on GitHub Pages. A GitHub Actions cron job runs on a schedule (independent of any visitor loading the site), logs into EVE's API with a stored authentication token, pulls the market and contract data for one specific structure, prices everything against Jita and Amarr, and writes the results as plain .json files back into the same git repository. The browser pages simply fetch() those JSON files and render tables with JavaScript. That's the entire trick: a cron job plus committed JSON is the database.

3. The five pages

  • index.html (market) — every sell order at the structure, judged against Jita. Filterable by category, price, verdict.
  • contracts.html — public item-exchange contracts at the structure, judged the same way, plus scam/scalp detection.
  • manual.html (Manual Lookup) — paste a contract's in-game item list, get an instant Jita/Amarr appraisal. Exists because ESI cannot show contracts privately assigned to an alliance or corp — this is the manual workaround.
  • war-room/ — alliance-shared doctrine readiness: "can we actually buy our fleet doctrines locally right now?"
  • trade-room/ — private (pilot + corp only) profit tooling: hauling cost model, buy-order bounty finder, manufacturing ideas, kill-loss demand signals.

All five load the same shared style.css, and each ships its own small JS file (or an inline <script> for the simpler pages) that fetches its JSON, filters/sorts it in memory, and re-renders an HTML table on every filter change. There is no routing library — every page is a genuinely separate file, linked by plain <a href> tags.

4. The data pipeline

Every ~30 minutes, .github/workflows/update-market.yml spins up a disposable Ubuntu runner and executes scripts/fetch-data.mjs. In order, that script:

  1. Exchanges a stored EVE SSO refresh token for a short-lived access token (OAuth2 refresh_token grant).
  2. Calls ESI's public regional order feed to discover which player structures exist in the target system (structure IDs leak through buy orders in the public feed even though sell orders don't).
  3. Calls the authenticated /markets/structures/{id}/ endpoint to pull the full order book for the known structure — this needs the character to have docking/market access there.
  4. Pulls public contracts at that structure from /contracts/public/{region}/, plus each authenticated character's own contract list (to catch alliance/corp-assigned ones — with the caveat in §10).
  5. Sends every item type ID seen so far to the Janice pricing API to get Jita 4-4 and Amarr min-sell reference prices (falling back to a 5-day median when an item has no live sell orders).
  6. Cross-references zKillboard for recent alliance losses (feeds the war room's "N lost/30d" tags) and a hand-maintained doctrine-fit snapshot for readiness checks.
  7. Diffs everything against the previous run to flag scalping (an item bought cheap and relisted higher, tracked by EVE's per-item item_id, which survives a contract sale).
  8. Writes out ~10 JSON files (data.json, contracts.json, trade.json, a scalp log, a zKillboard cache, a price-history cache, …) and git commit + git pushes them straight back to main.

GitHub Pages picks up the new commit automatically and republishes within about a minute; the CDN edge cache then takes up to ~10 minutes to catch up, which is why the site's JS/CSS assets are all versioned with a ?v=N query string bumped on every change — otherwise visitors could get new HTML paired with a stale cached script.

5. Auth & scopes

EVE's SSO uses standard OAuth2. A one-time local script (scripts/get-token.mjs) opens a browser login and captures a long-lived refresh token, which is stored as an encrypted GitHub Actions secret — never committed to the repo, never visible in logs. Two scopes matter here:

  • esi-markets.structure_markets.v1 — read a player structure's market order book (requires the character to actually have docking/market access there).
  • esi-contracts.read_character_contracts.v1 — read a character's own contracts (issuer/acceptor/assignee only — see §10 for why this doesn't fully solve alliance-contract visibility).

Each scan refreshes the access token fresh (they expire in ~20 minutes), so nothing long-lived beyond the refresh token itself needs to be trusted.

7. Hosting & the custom domain

GitHub Pages serves the repo's root directly. The custom domain (xhq7v.trade) points at GitHub Pages via Cloudflare DNS set to DNS-only ("grey cloud," not proxied) — GitHub Pages needs to see the real visitor to issue and renew its own Let's Encrypt certificate, and a proxying CDN in front of it can interfere with that. Cloudflare's CNAME flattening lets the domain's bare apex (no www.) point at GitHub Pages the same way a subdomain would. A CNAME file at the repo root tells GitHub Pages which domain to serve.

8. Keeping the scan alive

GitHub's cron scheduler is best-effort — on free public repos, scheduled runs at the top of common minutes (like :00 and :30) compete with everyone else's crons and can get silently delayed or dropped. Two mitigations are layered on top:

  • The cron itself is offset to off-beat minutes (7,37 * * * *) to dodge the stampede.
  • A local Windows Scheduled Task on the operator's own PC pings the workflow's workflow_dispatch trigger every 30 minutes whenever the machine is on, first checking whether a scan already ran recently so it never double-fires. It's launched invisibly (a VBScript wrapper hides the console window) via gh, the GitHub CLI, already authenticated on that machine.

9. Building the same thing from zero, without an AI pair-programmer

None of this requires exotic technology — it's a static site plus a scheduled script, which is one of the oldest patterns in web development (the "Jamstack" approach, or even older: this is basically how sites worked before dynamic backends were affordable). Here's the roadmap a developer would follow by hand:

Step 1 — Learn the domain's data source

Read EVE's ESI documentation end to end: which endpoints are public vs. authenticated, what OAuth scopes gate what, and the shape of market order / contract JSON responses. Budget a few days just reading docs and poking the API with curl before writing any code — this is true of integrating with any third-party API.

Step 2 — OAuth2, by hand

Register an application in EVE's developer portal, implement the OAuth2 "Authorization Code" flow once (a tiny local HTTP server that catches the redirect, exchanges the code for tokens) to mint one refresh token, then implement the much simpler "refresh_token" grant the recurring job actually uses. This is standard OAuth2 client code — any backend language's HTTP client and a basic understanding of Authorization: Bearer headers gets you there. Estimated effort: a day, mostly spent reading OAuth2 flow diagrams and testing.

Step 3 — Write the fetch/transform script

In any language with an HTTP client and JSON support (Node.js, Python, Go — doesn't matter), write a script that: gets a token, calls the market/contracts endpoints, calls a pricing API for reference values, computes a markup percentage per item, and writes the result to a JSON file. This is "extract, transform, load" — plain data-processing code, no framework needed. Expect iteration here: real API responses always have edge cases (items with no sell orders, paginated endpoints, capital ships that don't sell at the reference hub) that only show up once you're looking at live data. Estimated effort for a competent backend developer: 3-5 days to get a robust version, including error handling and retries.

Step 4 — Static frontend

Write plain HTML pages with <script> tags that fetch() the JSON and render an HTML table — this is "vanilla JS DOM manipulation," a skill that predates every modern frontend framework. A CSS file defines the visual theme. No build tooling (webpack, Vite, npm bundlers) is strictly required for a project this size — you can open the HTML file directly in a browser and see it work. Estimated effort: 1-2 weeks for someone comfortable with JavaScript and CSS, more if learning DOM APIs for the first time, building up filtering/sorting/search interactions one at a time.

Step 5 — Automate it

Write a GitHub Actions workflow file (YAML) that checks out the repo, installs Node, runs the script with secrets injected as environment variables, and commits+pushes any changed files on a cron schedule. GitHub's own Actions documentation and the actions/checkout / actions/setup-node examples cover this pattern directly. Estimated effort: half a day, mostly fighting YAML indentation and secret-scoping the first time.

Step 6 — Deploy and point a domain at it

Enable GitHub Pages in the repo settings, buy a domain from any registrar, add DNS records (or use Cloudflare) pointing it at GitHub Pages, and add a CNAME file. GitHub's own Pages docs walk through custom domains directly. Estimated effort: an afternoon, including waiting for DNS propagation and HTTPS certificate issuance.

Total, from scratch

For one experienced full-stack-adjacent developer already comfortable with JavaScript, HTTP/JSON, and OAuth2 concepts: roughly 2-4 weeks of focused part-time work to reach feature parity with the current market + contracts pages alone. The war room, trade room, and manual lookup pages each layer on additional domain logic (doctrine-fit modeling, hauling-cost math, scalp detection via persistent item IDs) that would each add several more days on top. None of it requires senior-level expertise — it's squarely "solid intermediate web developer" work — but there's a lot of small, fiddly domain-specific logic (capital ships not selling at Jita, fighters needing squadron-load math, EVE's contract items being immutable so they can be cached forever) that comes only from iterating against real data, which is where most of the actual time goes.

10. Where the corners were cut (on purpose)

  • No database. Git + JSON files work fine at this scale (thousands of rows, one writer, revisions every 30 minutes) but wouldn't scale to many structures or high write concurrency. A real multi-structure version would want Postgres/SQLite and an actual API layer.
  • Alliance-assigned contracts are genuinely invisible to ESI — the character-contracts endpoint only returns contracts where that specific character is the issuer, acceptor, or assignee, never ones merely "available to the alliance." This was confirmed empirically (an alt with alliance visibility in-game still returned zero contracts via ESI). The Manual Lookup page exists specifically to route around this ESI limitation, not fix it.
  • No server-side rate limiting or caching layer — relies on each upstream API's own limits (ESI, Janice, Fuzzwork) and on GitHub Pages' CDN for the frontend's own traffic.
  • The scheduler is best-effort, hence the local PC backup ping described in §8 — a "real" production deployment would run the cron on infrastructure with guaranteed scheduling (a small VPS, a managed cron service, etc.) instead of leaning on free CI minutes.
